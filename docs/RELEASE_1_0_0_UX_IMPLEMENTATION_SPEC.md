## 1. Цель и критерий продукта
1. Новый пользователь понимает четыре основных области и как добавить/найти объект без инструкции.
2. Основные действия с текущим контейнером — не более 2–3 переходов от открытия/QR; поиск/открытие сорта не прячется за промежуточными пустыми экранами.
3. Визуал уровня эталона, но реальные интерактивные Compose-компоненты (не фоновые PNG с нарисованными кнопками).
4. Цвет всегда дублируется словом/пиктограммой; графики отражают реальные данные и правильные биологические единицы; никакой «93% эффективности» без формулы, знаменателя и достаточных наблюдений.
5. Никакого ложного успеха: не показывать «синхронизировано», «напечатано», «создан отчёт», если результат не подтверждён. Неразработанные инструменты скрыть или явно пометить, а не имитировать.

## 2. Design system / готовые общие компоненты (P0)
**Цветовые токены-ориентиры по макету** (уточнять контраст в проверках): глубокий лесной \`#0B2E20\`, хвойный \`#144B31\`, оливковый \`#3F6B3A\`, мох \`#6E8F61\`, золото \`#C9A864\`, слоновая кость \`#F5E9D6\`, кремовый \`#EFE6D3\`, графит \`#1A1D1B\`. Светлые рабочие карточки — для плотной информации, тёмные поверхности — навигация/hero и контекст. Терракота — только по смыслу; красный — ошибки/критические статусы.

Шрифты: заголовки в выразительной гарнитуре с реальной кириллицей (ориентир Playfair Display), основной интерфейс — Montserrat/Inter с русским алфавитом, понятные fallback. Не встраивать без проверки лицензий. Размеры: базовый 16sp; поддержка font scale 1.5–1.6; hit-area >=48dp для значимых действий; минимум 4.5:1 для обычного текста. Ни при каких размерах надписи не перекрываются.

Сделать повторно используемые Compose-компоненты: \`BrandHeader\`, \`LabBottomNav\`, \`LabMetricCard\`, \`PlantFolderCard\`, \`PlantListRow\`, \`CulturePassportHero\`, \`StatusChip\`, \`FilterBottomSheet\`, \`ScreenOverflow\`, \`QuickActionSheet\`, \`TrendCard\`, \`TimelineEvent\`, \`EmptyState\`, \`ErrorState\`, \`LoadingSkeleton\`, \`ConfirmAction\`. Единые радиусы, внутренние отступы, высота строк, семантика иконок, состояния disabled/loading/success/failure. Не дублировать старые компоненты, а постепенно подключать текущие экраны к одной библиотеке.

**Визуальные статусы:** «В культуре», «Адаптация», «На контроле», «Карантин», «Архив», «Продано», «Списано». Не переопределять старые значения БД ради цветов; построить проверяемое сопоставление. Значение неопределено -> нейтральный статус, не зелёный.

## 3. Навигация и информационная архитектура (P0)
Нижнее меню фиксировано: \`Главная | Коллекция | [+] | Аналитика | Ещё\`.
- «+» — настоящая контекстная шторка: «Добавить сорт», «Новый контейнер», «Записать наблюдение», «Операция», «Задача», «Сканировать QR». Недоступные действия с объяснением отсутствующего контекста. Применять результат только после успешного сохранения.
- «Ещё»: сгруппированные секции «Лаборатория» (среды/рецептуры, ресурсы/склад, группы/места, маточники), «Работа» (журнал операций, календарь/задачи, эксперименты), «Справка» (база знаний), «Данные и приложение» (печать/принтер, резервные копии, импорт/экспорт, настройки, уведомления). Порядок — частота использования, а не технические имена.
- Три точки \`⋮\` на карточках только для действий с **текущим объектом**: редактировать, изменить обложку, метки, историю/аудит, архивировать с подтверждением. Глобальное «Ещё» — не то же самое.
- Поиск и одна кнопка \`Фильтры\` остаются на списках. Расширенные фильтры, диапазоны дат, сортировка, сохранённые пресеты — в отдельной шторке/форме; явные «Применить», «Сбросить», счётчик активных фильтров. Отмена не меняет применённые фильтры. Скролл, позиция и текст поиска сохраняются при возвращении.
- Android Back/жест возвращают на **один** экран; смена главных вкладок не сбрасывает пользовательский контекст без причины. Несохранённые формы — предупреждение. После QR и операции возврат строго туда, откуда открыли.

## 4. Поэкранный contract (P0/P1)
### UX-01 Заставка и вводный сценарий (P1)
Брендовый splash без долгой блокирующей анимации; onboarding только для первой установки. После обновления существующие данные и настройки -> сразу рабочий интерфейс. «Пропустить», повтор через настройки. Никакой обязательной регистрации/интернета.

### UX-02 Главная (P0)
Не более 4 основных оперативных карточек: коллекция/контейнеры, требуют внимания, активная работа/операции, задачи сегодня. Ниже две частые кнопки по реальным данным; «Сегодня» + ближайшие задачи/критические сигналы. Сводки строятся SQL-агрегатами; числа имеют подпись единицы/источника. Карточка нажимается целиком и ведёт в соответствующий фильтрованный реестр. Нет дубля «Коллекция» рядом с тем же входом. Лёгкий декоративный ботанический hero не перекрывает текст.

**Приёмка:** из каждой KPI карточки открывается правильная выборка; пустая база не показывает фиктивные числа; на 360dp первый экран читаем без горизонтального скролла.

### UX-03 Коллекция и собственная визуализация (P0, ключевой новый функционал)
Иерархия «сорт/вид -> контейнеры»; режим \`Плитки / Список\`. Карточка-папка: фото-обложка, небольшая собственная иконка/пиктограмма, имя, число активных и всех контейнеров (без смешения с растениями), состояния/метки и сигнал проблемы. Основные фото — реальные, выбранные владельцем; при отсутствии фото — аккуратная ботаническая пиктограмма, **не изображение другого сорта**.
Редактор внешнего вида из \`⋮ -> Оформить карточку\`: выбрать изображение из телефона, кадрировать/масштабировать, применить; отдельно выбрать одну из встроенных пиктограмм, цвет метки, заменить/убрать. Настройка на уровне сорта, не привязана к конкретному контейнеру. Взаимодействие не удаляет исходные фотографии контейнеров. Плейсхолдер и статус доступны и без медиа. Поиск — по названию/коду, фильтр — отдельный экран; переключение режимов запоминается.
Тап на папку -> экран сорта с быстрым доступом к полному SQL-постраничному реестру контейнеров, без вторичного «открыть всё» для основного действия.

**Data contract:** добавить аддитивную таблицу визуального оформления сорта с FK \`plant_id\`, уникальной пиктограммой \`icon_key\`, ссылкой на приватный \`cover_filename\`, параметрами обрезки (если нужны), обновлением/аудитом. Оригинал файла и миниатюра — в приватном хранилище; миниатюра может пересоздаваться, не хранить base64 в SQLite. Изображение — не внешний URL, работает полностью офлайн. При замене/архивировании учитывать подтверждённые исторические связи. Backup экспортирует оригинал, ссылку, оформление и корректно восстанавливает, включая старые архивы, где визуального оформления нет. Показ сетки не грузит тысячи bitmap в память одновременно.
 
**Приёмка:** назначение -> перезапуск -> сохранено; без картинки отображается корректный дефолт; offline работает; восстановление бэкапа сохраняет картинку; 200/2000 сортов не вызывают OOM; ошибки выбора файла не меняют текущую обложку.

### UX-04 Экран сорта (P0)
Hero с названием и визуальной обложкой, краткая сводка, редактирование; вкладки \`Контейнеры / Обзор / История\` с **Контейнерами** по умолчанию (самый частый путь). Контейнеры через существующий SQL-pagination; не создавать второй каталог с несогласованными фильтрами. «Новый контейнер» предзаполняет сорт. Сорт и контейнер — разные сущности, один паспорт не должен подменять другой.

### UX-05 Паспорт контейнера (P0)
Вверху код/ID, этап, статус, пассаж, рецептура/версия, место, подтверждённый тип учёта, фото при наличии. Четыре основные функциональные кнопки/вкладки \`Рост / Среда / Операции / История\`. Быстрые отдельные действия «Наблюдение», «Пересадка», «Потери», «Задача» по текущему статусу; «Этикетка»/«Фото» визуально доступны, а не захоронены в служебном меню. Печатать код из той же БД (не сгенерированный для примера). Реальная линейная навигация и обратная связь после записи.

### UX-06 Рост (P1)
График по датам и отдельно по единицам (экспланты/побеги/растения); реальные измерения и аннотации пересадок/потерь/смен среды/фото/заражений. Выбор 7/30/90/всё; пустая серия = «Нет измерений»; нельзя рассчитывать рост от 0 или из NULL без явного правила. Текущие учётные остатки и наблюдаемые измерения не смешивать. Нажатие точки открывает первичную запись и её историю правок.

### UX-07 Операции / хронология (P1)
Единая лента с иконкой типа, дата/время, код контейнера, числовое изменение с **единицей**, причина, источник и путь к записи/аудиту. Действия могут быть недоступны по биологическим ограничениям: показывать объяснение, не маскировать запись ошибок. Журнал и история контейнера используют одни реальные события, не копии со своим состоянием. Фильтр отдельной формой.

### UX-08 Среды и рецептуры (P1)
Карточки состава, назначение/статус жизненного цикла/версия/использование, кнопки просмотра и редактирования; список с поиском и отдельными фильтрами. Научный результат показывать только при явной метрике, валидных сравнимых группах и достаточном числе наблюдений; иначе «Недостаточно данных». Партию приготовления не выдавать за обязательную рецептуру. Фактически введённые навески отделять от расчётных.

### UX-09 Аналитика (P1)
Подразделы \`Обзор / Рост / Операции / Среды / Потери / Адаптация\`. Все показатели с раскрываемой формулой, окном дат, количеством наблюдений, статусом достаточности. Графики не суммируют разные типы биоматериала. Никаких демо-значений в production. Для больших данных SQL-агрегация и постраничные подробности; доступен переход к исходным наблюдениям.

### UX-10 Календарь и задачи (P1)
Рабочий календарь и список ближайших задач, статус, приоритет, связь с контейнером и необходимой операцией, исправление/закрытие/отмена с аудитом. Быстрый переход из задачи к действию, завершение задачи только после фактического сохранения результата, без придуманных нормативов и сроков. Повторяющиеся задачи — только при явно настроенном пользователем правиле, с защитой от дублей.

### UX-11 Ресурсы / склад (P1)
Раздельно расходники, реактивы, инвентарь; карточки с единицами, количеством и порогом. Приход/расход как учётные действия с датой и причиной, а не только произвольная правка остатка. В неготовых подразделах не показывать фальшивые динамические полоски остатка. Хранить операционные события и отчёт по ним, если включается складское движение.

### UX-12 База знаний (P1)
Не имитация «популярных статей». Настоящий локальный, доступный офлайн каталог пользовательских протоколов/методик/заметок со структурой \`Название / растения / версия / описание / источник URL или DOI (если есть) / дата / теги\`, поиск и редактирование. Отделить собственные протоколы от проверенных публикаций. Не переносить автоматически непроверенные сведения и не объявлять 500 статей изученными. Новые записи включать в backup.

### UX-13 Настройки / данные / «Ещё» (P0/P1)
Группировка категорий без смешения: визуал/профиль, пользовательские метки, оборудование/принтер, данные/архив, экспорт, уведомления, справка. Если облачная синхронизация не реализована/не подтверждена — не показывать её как действующую. Нельзя потерять ранее действовавшие импорт/экспорт и резервные копии. Экспорт CSV/PDF/других форматов в интерфейсе допускается только если реально генерирует открываемые файлы. Переключение темы необязательно, если темная лесная тема читаема и проверена.

### UX-14 Фильтры и overflow (P0)
\`Фильтры\` в отдельном Compose bottom sheet / полноэкранной форме на 360dp. Критерии по текущему разделу, сохранение пресета, временные изменения до нажатия «Применить», счётчик итоговой выборки без полного чтения 20k строк. Контекстные \`⋮\` имеют типизированные действия и подтверждение для архивирования. Главное окно после закрытия фильтра не перерисовывает весь список с потерей позиции.

## 5. Приоритет реализации / зависимость PR
**Этап A (P0):** единая тема/иконки/карточки/нижняя навигация/«+»/«Ещё»/обособленные фильтры. Вначале улучшить основные сценарии на действующих данных.
**Этап B (P0):** таблица визуальных настроек сорта, выбор/обрезка изображений, загрузка миниатюр, история/backup; плитка/список; паспорт сорта и контейнера.
**Этап C (P1):** графики роста, хронология, средства, задачи, аналитика; убедиться, что источники данных реальны, отсутствует двойной счёт.
**Этап D (P1):** ресурсы, протоколы/база знаний, сценарии импорта/экспорта, системные экраны и редкие ошибки.
**Этап E (P0 стабилизация):** E2E и UI regressions, восстановление старых данных, проверка 20k объектов, аудит каждого экрана на смартфоне, устранение дефектов, подписанная 1.0.0.

Это внутренние PR-этапы, **не обещание пяти промежуточных APK**. Разработка допускает отдельные безопасные feature-ветки от проверенного 0.9 базиса; никаких изменений в основном релизе без зелёного CI и корректной миграции.

## 6. Миграции, резервное копирование и ограничения
- Базовая SQLite на 0.9 RC — v10. Для новых данных оформления/склада/знаний потребуется **аддитивная** версия (номер определить по фактическому DDL), без переписывания старых измерений/сред/кодовых связей.
- Backup JSON/ZIP старых версий продолжает восстанавливаться. Новые таблицы/файлы включить в проверенный порядок экспорта; старые архивы применяют безопасные defaults. Фото сортов не путать с \`culture_photos\`. Импорт/восстановление на **изолированной** БД с проверкой FK и целостности перед заменой пользовательской.
- Существующий лимит 50MB JSON/500MB ZIP в импорте нужно проверить на реальных больших базах; при необходимости доработать потоковое восстановление, не заявлять масштабируемость без проверки. Экспорт не должен терять скрытые фото, архивные сущности, этикетки и происхождение.
- Редактор NIIMBOT 0.9 RC, шаблоны, кириллические шрифты, B/I/U и Bluetooth transport сохранить. Прямую печать объявить подтверждённой только после теста модели владельца, QR и 10 уникальных наклеек; возможно оставить техническую отметку «непроверенная модель» до приёмки.

## 7. Матрица приёмки 1.0.0
- **NAV:** телефон 360/393/430 dp; клавиатура; системная кнопка/жест назад; между вкладками; через QR; сохранение поиска, фильтра, скролла, несохранённых форм и контекста.
- **VIS:** экран каждого раздела и состояния: нормальный, пустой, загрузка, ошибка, много контента; масштаб системного текста 150/160%; читаемость кириллицы, контраст и тап-области >=48dp; реальные иконки описывают действие; никакого перекрытия/обрезки.
- **COL:** новая обложка, смена, удаление, поворот/кадрирование, встроенная пиктограмма; восстановление после перезапуска и из ZIP; 0/1/2000 сортов; старые сорта без оформления работают без ошибки.
- **LAB:** ввод/редактирование контейнера, наблюдение, split/merge, смена среды, потеря, инцидент, задача, история, отмена, продажа; доказанное отсутствие смешивания числовых типов и потери audit.
- **MED:** расчёт рецептуры vs фактическая партия; null vs 0; ручное/дочернее наследование версии среды; backup.
- **PERF:** 20 000 контейнеров (поиск, фильтры, переход по QR, сортировка, группировка, массовое действие), нет full-table UI-load и зависания при обычных операциях. Фиксировать измерения времени и памяти на тестовой аппаратной конфигурации.
- **PRINT:** QR указывает на верный ID; после обновления 0.8->0.9->1.0 не теряется редактор/шаблоны; физические испытания NIIMBOT отдельно по acceptance из #19.
- **BUILD:** GitHub PR CI (Python/SQLite, Kotlin unit, assembleDebug, instrumented UI), Android isolated migration, резервные копии; стабильная версия подписана прежним сертификатом, update поверх установленной версии успешен.
- **PROVENANCE:** отображаемые проценты/эффективность/остатки можно проследить до данных, формулы и единицы. При отсутствии данных — «Недостаточно данных», никаких фиктивных KPI.

**Статус готовности:** все пункты из Issue #21, покрытие названных сценариев, зелёный CI, визуальная проверка на физическом устройстве владельца, восстановление существующей базы и подтверждение сертификата. До этого версия только кандидат, без заявления «1.0.0 выполнена полностью».
