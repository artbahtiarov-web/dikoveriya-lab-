# Диковерия LAB — комплексный релиз 0.7.2: Центр управления лабораторией

**Дата:** 2026-11-12 UTC. **База:** main `2f1f4d75fa388a3c3cd24433fe8c78c96cdfc939` (версия 0.7.1), Issue #1/#3/#4 и утверждённое пользователем ТЗ на масштабирование 10–20 тысяч контейнеров. **Разработка:** PR #17 `release/0.7.2-lab-command-center`, `0.7.2` в финальном кандидате, только после полной CI-приёмки.

## Понятные названия и один шаг с главного экрана

| Было | Стало | Действие нажатием |
|---|---|---|
| In vitro | **В пробирках** | Контейнеры стерильной культуры с фильтрами |
| Нужен контроль | **Требуют внимания** | Проблемные контейнеры, причина, важность, срок и результат |
| Адаптация и рост | **Растут** | Адаптация и доращивание; фактические замеры и работа |
| Задачи | **Задачи** | Сроки, приоритеты, текущие и завершённые дела |

Карточки нажимаются **целиком**, содержат стрелку-подсказку, работают также при нуле. Цвет не единственный сигнал: текст статуса, причина, тип важности, срок. «В пробирках» и «Растут» показывают **активные** контейнеры в соответствующих этапах; «Требуют внимания» — активные со статусом контроля/карантина или открытым зарегистрированным случаем; «Задачи» — незавершённые со сроком `due_at <= now`. Один контейнер может одновременно присутствовать в культуре и в контрольном реестре; это разные аспекты, а не ошибка двойного счёта. Для архивного статуса причины не сочиняются.

## Полная работа с крупной коллекцией

1. **SQL-реестры**: поиск по номеру/сорту/названию группы/месту; фильтры сорт, рецептура и версия, стадия, состояние, группа, структурированный адрес, период, фактический последний замер; сортировка по дате, названию, месту, отдельно по измеренным побегам или растениям. SQLite `COUNT(*)`, `LIMIT/OFFSET` по 40, индексы, фоновые запросы `Dispatchers.IO`. Прямой QR → индексный ID, без сканирования списка в памяти.
2. **Коллекция**: агрегированные SQL-счётчики сортов, переход к точному сорту и прямому реестру его контейнеров; не материализовать 10 тысяч строк для обычной домашней страницы; последние пять — короткая подсказка, не весь реестр.
3. **Группы контейнеров**: отдельно от партии питательной среды и категории биоматериала; ручная группа только для одного сорта и согласованного маточника; одна подтверждённая операция разделения с двумя и более дочерними контейнерами создаёт общую производственную группу по факту происхождения. При исторических данных ничего не группируется задним числом. Каждый контейнер сохраняет ID, родителя/пассаж/количество/среду/историю.
4. **Расположение**: Помещение → Стеллаж → Полка → Позиция с проверкой родительского уровня и уникальным адресом. Данные прежнего текстового поля `location` не удаляются автоматически; только ручная запись нового точного адреса. Перемещения логируются с исходным и конечным местом, связью с транзакционной операцией.
5. **Контроль**: отдельная сущность `control_cases`: причина, приоритет проблемы `Обычный/Важный/Критический`, дата/срок, требуемое действие, результат и факт закрытия. Если назначен срок, создаётся задача только по явно введённой дате. Просроченность срока и критичность проблемы показываются независимо. Закрытие проблемы не отменяет статус карантина самостоятельно — паспорт меняется осознанно.
6. **Задачи**: открытые/сегодня/просроченные/7 дней/все/выполненные; фильтры срок, приоритет, тип работы, растение, рецепт, поиск, пользовательские именованные наборы. Незаверенные старые задачи имеют приоритет «Не задан», а не придуманную срочность; приоритет изменяется с аудируемой историей. Из задачи «Осмотр» один переход к измерению нужного контейнера.
7. **Пакетные операции**: выделить до 200 контейнеров → создать группу, переместить, назначить контроль, поставить задачи, выбрать совместимую утверждённую среду или записать общую текстовую заметку. Все изменения одной операции — в одной транзакции. Некорректный элемент приводит к откату всей партии. Смена среды сохраняет `medium_recipe_id` и обнуляет прежнюю необязательную партию, количественные показатели не меняются. Общая заметка НЕ создаёт фиктивные экспланты/побеги/растения. Для печати — ZIP из индивидуальных PNG этикеток 40×12 с собственными ID и QR; NIIMBOT должен импортировать/печатать после распаковки, прямой Bluetooth не реализован.
8. **Фильтры**: запоминаются при возвращении назад/вращении экрана; именованные наборы `saved_views` — в SQLite и в резервной копии. По умолчанию ни один статус, сорт, рецепт или генетическая линия не придумываются.

## SQLite 9 и сохранность данных

* Версия SQLite `8 → 9` аддитивная, данные исходных `cultures`, `events`, `culture_measurements`, `assessments`, `recipes`, `recipe_parts`, `culture_audit` не перезаписываются.
* Таблицы v9: `production_groups`, `culture_groups`, `group_history`, `storage_locations`, `culture_storage`, `storage_movements`, `control_cases`, `control_case_history`, `task_metadata`, `task_history`, `saved_views`.
* Индексы для stage/status/даты, места, сред, групп, причин контроля и задач. Ограничения внешних ключей активны, смена места и массовые действия транзакционные.
* ZIP/JSON: схема экспорта = 9; старые версии 4–8 принимаются. `BACKUP_ORDER_V8` оставлен как неизменный исторический срез; дополнительные таблицы последовательно добавлены в порядок; самоссылочный список `storage_locations` экспортируется по ID с родителями раньше потомков.
* Идентификатор Android, существующий сертификат/keystore, FileProvider, QR-схема, рецептурные расчёты и существующая история не меняются.
* **Риски**: старое ограничение JSON `50MB` и ZIP `500MB` при чрезвычайно большой истории / фото; формат резервирования с потоковой сериализацией потребует отдельного решения до работы с очень большими архивами. Пагинация `LIMIT/OFFSET` работает для десятков тысяч, но на очень глубокой прокрутке cursor/keyset paging предпочтительнее. Никаких обобщённых коэффициентов эффективности без сопоставимых единиц и контрольных групп.

## Приёмка и честные пределы проверки

- Source/Python/SQLite regression: `qa/test_v9_command_center.py`, старые QA; реальный SQL DDL v9, v8-fixture, foreign_key_check, rollback, 10k/20k синтетических записей и SQL explain/index; **не подменяет** миграцию реальной пользовательской БД.
- JVM/Android: `:app:testDebugUnitTest`, `:app:assembleDebug`, Compose UI тесты при 360dp и 430dp + увеличенный шрифт, проверка переходов по KPI/Back/кнопкам и QR.
- Только после PR CI green, проверки миграции/backup, низкого риска данных разрешено merge. После merge требуется отдельный успешный постоянный **signed release APK** с подтверждением сертификата и артефакта. Не применять PR debug APK поверх установленного приложения.
- На физическом Android ещё проверить обновление БД 8→9, сканирование маркировки, скорость при рабочем наборе, качество термоэтикетки и отсутствие обрезаний при 360–430dp. **Нормы роста, сроков адаптации, частоты контролей не задаются автоматически**.

## Итог ревизии и последние технические проверки

- Источник до версии: `main` 0.7.1; ветка PR #17 содержит все 4 полноценных рабочих экрана и тестовый набор на 20 000 записей. На раннем коммите PR проверка SQLite/Python, JVM и `:app:assembleDebug` была **success**: https://github.com/artbahtiarov-web/dikoveriya-lab-/actions/runs/43246242337 .
- Обнаруженные ошибки предыдущих запусков исправлены в том же PR: синтаксис generic-expression в Kotlin; nullable payload сканера; устаревшие ожидания test'ов миграции/QR; недоступный переход к адресам; совместимость текстового изменения места с структурированным адресом. Новые Android instrumentation tests проверяют KPI-навигацию и onUpgrade(8,9) на изолированной базе.
- Дополнительно: массовая совместимая смена версии среды и отдельная общая текстовая заметка, экспорт до 200 индивидуальных этикеток в один ZIP; **это не команда Bluetooth-печати**. Фильтры по относительному периоду и введённым датам сохраняются с именованными представлениями, а не теряются при их восстановлении.
- Известные ограничения реального запуска: для больших групп история в старых служебных экранах всё ещё может вызывать неограниченную загрузку; новый путь с главного экрана и коллекции использует SQL-пагинацию, но полная оптимизация всех редких старых диалогов — следующий технический этап. Существующий backup JSON строится в памяти, поэтому на объёмных фото/журналах может потребоваться будущий потоковый формат. Все показатели корректны по типам измерений, а «Растут» не означает процент успешности.
- Отдельный Android UI-run финального SHA и подписанный APK должны быть подтверждены фактическими результатами после окончания PR; до этого не утверждать, что стабильная сборка готова.
