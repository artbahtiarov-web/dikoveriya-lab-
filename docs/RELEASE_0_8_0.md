## Договор по пользовательскому сценарию

Цель — лаборант без ИТ-подготовки, от первого контейнера до десятков тысяч. Переход с главного: **В пробирках / Требуют внимания / Растут / Задачи**. Главное не показывает случайные утилизированные контейнеры, кнопку «Коллекция» или второй вход в «Среды». Нижняя вкладка понятнее: **«Растения»**; внутри один поиск, компактная сортировка и «Добавить сорт». Нажатие на сорт **сразу** показывает полный постраничный список его контейнеров, без промежуточного каталога/5 последних.

Создание контейнера: сорт, исходные **независимые nullable** измерения, явная основная единица учёта, пассаж, этап, версия среды, маточник, точное или историческое текстовое место; после сохранения показывать карточку созданного контейнера. Если указано >1 положительных измерений, не выбирать максимальное число как подтверждённую единицу «экспланты/побеги/растения»; оператор её подтверждает явно. Первоначальное наблюдение = `baseline`, не событие измерения роста; задачи требуют реальной даты.

Достоверность: отделить расчёт рецепта от документального приготовления. Устаревшая форма с автоподстановкой расчётной массы убрана из доступных режимов. В новой форме приготовления все **фактические** числа вводятся отдельно. Аналитика помечает последние измерения как наблюдения, не фактические складские остатки; закрытые контейнеры не учитываются как активные наблюдения. Заражение в осмотре предлагает поставить контроль, но не переводит автоматически в карантин. Регистрируемые случаи имеют причину, важность, срок и действие; назначенная по контролю задача связана с ним через `case_tasks` и закрывается вместе с контрольным событием. Старым v9 задачам не приписывают догадками связь с прежним случаем.

Из окна контейнера доступны **наблюдение, пересадка, потери, назначение задачи, фото, редактор этикетки, четыре подробных раздела**. Состояния и переходы сохраняют audit before/after. Записи об утилизированных, проданных и аннулированных объектах не удаляются.

## Редактор этикеток 40×12 — объём реализации 0.8.0

Это больше не окно «просто QR». Полноэкранный Compose-холст с координатами в **миллиметрах** (40 × 12), превью и DPI 203/300:
- Перетаскивание пальцем, выбор элемента касанием и через явные кнопки, перемещение стрелками на 0,5 мм, сетка и привязка;
- Размеры элементов, высота шрифта, шрифт Sans/Serif/Mono, жирность, выравнивание и поворот;
- Поля: QR, название сорта, код, пассаж, рецептура/версия, дата, маточник, заметка, произвольный текст; добавление, скрытие и удаление необязательных слоёв;
- Undo/Redo, сброс к базовому макету, предупреждения о перекрытии и чрезмерно мелком тексте;
- Сохранение индивидуального дизайна контейнера, именованные собственные шаблоны, применение/удаление шаблона;
- Экспорт PNG с реальным размером, физическим PNG `pHYs`, ZXing QR и Android Share через существующий ограниченный `FileProvider`;
- Массовая генерация PNG ZIP сохраняет уникальный ID каждого контейнера (ни один QR не одинаковый); отдельная физическая печать NIIMBOT должна подтверждаться реальным устройством, **Bluetooth SDK в 0.8.0 не заявлен**.

QR и код контейнера защищены от удаления из макета, позиционирование ограничено размером носителя, шаблоны сериализуются/валидируются в JSON. Масштабирование превью не меняет миллиметры фактической печати.

## Записи, изменение и архив

Новые транзакционные операции `entity_changes` (состояние до/после, причина) и `entity_archives` для справочников. Компонент можно исправить/архивировать прямо из карточки в «Средах». Сорт можно исправить/архивировать из списка, только если **не имеет связей** с контейнерами, маточниками, группами, рецептурами; удаление связанных сортов недопустимо. Фото можно исправить и убрать из видимого списка без физического удаления файла. Задача отменяется с причиной, доступна в отдельном списке «Отменённые», но история сохраняется. Для операций с биологическим количеством остаются специальные транзакционные корректировки/отмена; общий `delete` на паспорт не добавлять.

## Совместимость и технические проверки

- SQLite **9→10 строго аддитивно**: `label_templates`, `label_overrides`, `entity_archives`, `entity_changes`, `case_tasks`. Исходные cultures / counts / measurements / medium_recipe_id / genealogy / photos / tasks не переразмечать.
- JSON/ZIP схемы 4–9 продолжают восстанавливаться, новый экспорт = 10 с точным порядком родительских таблиц и связей. Исторические архивы не выдают за новые события.
- ZIP backup **пишется потоком из SQLite** вместо построения глобального JSON в памяти; фото включаются все, включая скрытые из UI. Существующая операция восстановления всё ещё имеет лимит JSON 50 MB / ZIP 500 MB — это ограничение необходимо тестировать и не скрывать.
- `appId` и сертификат Android не менять. PR: `qa`/SQLite/JUnit `:app:testDebugUnitTest`, `:app:assembleDebug`; Android connected tests 360/430dp + 150/160% шрифта, миграция SQLite9→10 с изолированным вводом `null != 0`, реальная ZXing-декодировка дизайнера при обоих DPI, семантика редактора и Back.
- При провале PR CI — исправлять в **том же PR**; до зелёного статуса PR и исключения опасных миграций **не объединять в main**. После merge проверить signed release workflow на фактическом SHA, сертификат и реальный APK-артефакт.

## Незавершённые физические и продуктовые проверки

Даже успешные CI не подтверждают качество термопечати на конкретном NIIMBOT, обновление **личной** базы владельца, скорость 20 тыс. контейнеров на его Android, манипуляции из всех редких служебных экранов, а также автономное восстановление фотоархива >50MB JSON. Прямой Bluetooth-протокол печати не реализуется под видом Share. Честно фиксировать любые непокрытые сценарии и не объявлять 10/10 по существованию кода.
