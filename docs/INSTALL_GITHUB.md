# Установка исходников в существующий репозиторий GitHub

Репозиторий: `artbahtiarov-web/dikoveriya-lab-` (дефис на конце важен).

## Способ 1 — GitHub через браузер, без GitHub Desktop

1. Распакуй архив на телефоне или компьютере **только для того, чтобы открыть** файл `.github/workflows/build-apk.yml` (его содержимое нужно для следующего шага). Исходный архив оставь целым.
2. В GitHub открой `.github/workflows/build-apk.yml`, нажми карандаш. **Полностью замени всё содержимое** содержимым одноимённого файла из архива. Нажми `Commit changes`. Первый запуск от этого изменения может быть красным — в репозитории пока остался старый код.
3. На главной странице репозитория нажми `Add file` → `Upload files`. Загрузи **сам архив под именем `dikoveriya-lab-complete.zip`**, не распаковывая его. Нажми `Commit changes` в ветку `main`.
4. Новый GitHub Actions workflow сам распакует файлы для сборки. Он также попробует записать исправленные исходники в `main`. Для записи нужен режим `Settings` → `Actions` → `General` → `Workflow permissions` → `Read and write permissions`, если политика репозитория позволяет. Если запись не разрешена, он всё равно попытается собрать проект из распакованного архива; в таком случае для дальнейшей разработки надо будет отдельно сохранить файлы в репозитории.
5. Открой `Actions` → последний `Build Android APK`. При зелёном результате открой запуск → `Artifacts` → `dikoveriya-lab-debug`, скачай архив и извлеки `app-debug.apk`.
6. Если сборка красная — не меняй Gradle-файлы наугад; сохрани ссылку на конкретный job и **первую строку `e:`, `error:` или `FAILURE` в шаге Test core calculations and compile APK**.

**Важно:** если старый APK установлен, новый debug APK может не установиться поверх него из-за разных подписей. Пока нет полноценной резервной копии старой установленной версии, **не удаляй её**.

## Способ 2 — GitHub Desktop (надёжнее)

1. Клонируй репозиторий `artbahtiarov-web/dikoveriya-lab-` через GitHub Desktop.
2. Распакуй архив исходников. Скопируй **всё содержимое его корня** (`app`, `.github`, `docs`, `qa`, `README.md`, `build.gradle.kts`, `settings.gradle.kts`, `gradle.properties`) поверх одноимённых файлов клона, не трогая папку `.git`.
3. В GitHub Desktop нажми `Commit to main` → `Push origin`.
4. Проверь `Actions`; при зелёной сборке скачай APK из Artifacts.

### Почему не подходит загрузка только `MainActivity.kt` и `app/build.gradle.kts`

Новая система имеет отдельные полноценные файлы модели, базы данных, бэкапа, форм, сканера, CSV и тестов. Если заменить только два файла из старого прототипа, проект будет неполным.

## Постоянная подпись — важно до ввода реальных данных

Для стабильных обновлений всех будущих APK нужно использовать **один и тот же ключ подписи**. Создай `.jks` на собственном компьютере и храни копию в безопасном месте, не в публичном репозитории.

В GitHub Settings → Secrets and variables → Actions создаются четыре репозиторных секрета:

- `LAB_KEYSTORE_B64`: содержимое JKS, кодированное Base64 в одну строку;
- `LAB_KEYSTORE_PASS`: пароль хранилища;
- `LAB_KEY_ALIAS`: псевдоним ключа;
- `LAB_KEY_PASS`: пароль ключа.

Workflow восстанавливает временный JKS из секрета и подписывает debug APK. **Ни секреты, ни сам ключ нельзя выкладывать в исходники.** Для первого перехода с ранее установленного APK, подписанного другим ключом, простое обновление без удаления может быть технически невозможно; сначала экспортируй резервную копию из работающей версии.

## Не делай до первого успешного теста

Не удаляй старое приложение, не вводи всю коммерческую базу в dev-сборку, не сохраняй единственную резервную копию на том же телефоне. Соединение с Google и прямое управление NIIMBOT ещё не проверены и не должны считаться готовыми.
